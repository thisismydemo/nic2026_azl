# cluster-configure / sdn-network

Logical networks and network security groups for an Azure Local instance with **SDN enabled by Azure Arc** (network-design §4.6, D-048). The values (prefixes, VLANs, pools, DNS servers, rules) come from the environment file (`sdn`, `logical_networks`, `network_security_groups`); this README names none of them.

| Step | How | Notes |
|---|---|---|
| 1. DNS record | A record `<SDNPrefix>-NC.<dns zone>` → the 5th address of the infrastructure IP range | Local Identity nodes cannot register it themselves ([Troubleshoot SDN](https://learn.microsoft.com/azure/azure-local/manage/sdn-troubleshooting)) |
| 2. Enable SDN (once, permanent) | on a node, as the deployment admin: `Add-EceFeature -Name NC -SDNPrefix <prefix> -AcknowledgeMaintenanceWindow -AcknowledgeDNSRecordCreation` | Learn: [Enable SDN integration](https://learn.microsoft.com/azure/azure-local/deploy/enable-sdn-integration); up to 20 minutes; cannot be rolled back |
| 3. Wait | more than 5 minutes after step 2 | network interface changes made inside that window can be lost (known issue) |
| 4. Networks and NSGs (**the build path**) | `scripts/Invoke-SdnNetworkCli.ps1 -WhatIf`, then without `-WhatIf` | Azure CLI `az stack-hci-vm` (extension 1.15.1 or later), in Microsoft's order: every logical network, then every NSG and its rules, then each NSG attached with `lnet update --network-security-group` only. Idempotent: existing Succeeded resources are left alone; the DNS servers are sent once, at create, and never again |
| 5. Unmanaged Hyper-V VMs on the same VLANs | on the node hosting the VM: `SdnDiagnostics` `Get-SdnVMNetworkAdapterPortProfile`, then `Set-SdnVMNetworkAdapterPortProfile -ProfileId ([guid]::Empty) -ProfileData 2` if no profile is returned | Learn: [VMs created outside of Windows Admin Center](https://learn.microsoft.com/azure/azure-local/manage/manage-default-network-access-policies-virtual-machines-23h2#vms-created-outside-of-windows-admin-center). NSGs do not cover these VMs; the firewall and the host firewall do |

`bicep/` (`main.bicep`; the environment parameter files `networks-only.generated.bicepparam` and `main.generated.bicepparam`, which are not published; `main.example.bicepparam` with neutral values; driven by `scripts/Invoke-SdnNetworkDeploy.ps1`) is kept for the what-if and as a reference template. Do not use it to attach NSGs to logical networks that already exist: its second pass sends the whole logical network again, DNS servers included, and re-applying the same DNS servers to an existing logical network fails on this build (known issue; never edit logical-network DNS in the portal either).

Rules of the road (Learn): manage these only from Azure (never SDN Express or Windows Admin Center); NSGs cover Azure Local VMs only; logical network gateway, pools, prefix, VLAN and switch are immutable after creation; every NSG ends with an explicit deny so an empty rule set never blocks by surprise; an NSG delete can hang (teardown tolerates it).
